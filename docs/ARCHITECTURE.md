# LS-PrePost-MCP 产品与工程顶层设计

状态：2026-10-01 设计基线；描述目标架构和迁移顺序，不表示这些结构已全部实现。当前代码/原生验收基线为 `795a354`。机器计划见 `src/ls_prepost_mcp/data/development_plan.json`；具体缺口见 [待开发清单](BACKLOG_REVIEW_2026-10-01.md)。

## 1. 产品目标与交付对象

让用户用自然语言，在明确模型、单位、实体选择、结果含义和软件版本的前提下，连续完成 LS-PrePost 常用前处理与后处理，获得可检查、可重开、可复用的工程产物。

用户不需要为了常见任务编写 cfile/SCL/Python；需要高级脚本时仍保留五种正式入口。用户得到的是任务完成结果和可复用流程，而不是一串没有验证的命令。目标用户是已有 LS-PrePost/LS-DYNA 工程工作流的使用者；MCP 不替用户隐式决定材料、单位、接触或工程判断标准。

最终交付包括：MCP 服务、任务型 Skills、版本适配器、工程工作流/模板、合成验收集和真实能力矩阵。公开仓库只交付通用代码/合成资料，不分发厂商软件手册、用户模型及派生数据。

当前不是完整 LS-PrePost 替代品，也没有全菜单覆盖。几何建模/几何驱动划网格按用户要求后排；4.11 排除；求解调度与许可证资源另外定义。

## 2. 首个实用版本：用三条流程定义完成

0.4.0 仍是开发版本。首个实用版本须完成下面三条有边界的流程，而不是继续以新增工具个数作为完成依据。首轮明确 Windows 4.13.4 可见 GUI；旧版和两种无 GUI 模式各自验收。

### WF-MESH：常用网格编辑与检查

用户任务示例：“打开这个 k 文件，按部件选择网格，修改指定节点/单元，合并重复节点，修正法向和编号，检查后保存。”

步骤：输入副本与单位 → 模型/实体识别 → 可见范围与选区 → 编辑预览/检查点 → 原生编辑 → 坐标/连接/引用核对 → 原生质量/关键字检查 → 显式质量门槛 → 保存 k → 原生重开核对。

首轮冻结范围：标准节点、线性壳/实体网格；显式/部件/区域/基本拓扑选择；平移/旋转、节点位置/连接编辑、重复节点、法向、编号；支持操作的范围必须写入矩阵。复杂复合材料、任意自动修复、全部关键字引用不默认包含。

退出标准：成功例得到可重开的输出；指定未选实体保持；坏网格/错误引用按门槛停止；原文件不变；失败有可恢复基线；代表规模实测并公布边界。当前 20000 全量验证限制必须通过分块/按实体访问设计处理，不能仅修改常量。

### WF-POST：具有明确语义的工程后处理

用户任务示例：“提取指定部件/单元的应力和历史量，计算三轴度/Lode，输出力—位移或应力—应变，检查能量并生成图表。”

步骤：识别 d3plot/ASCII/binout 与文件族 → 明确实体/时段/量/单位/层/积分点/坐标/平均 → 原生提取 → 验证有效实体和输出完整性 → 工程计算 → 曲线/云图/数据一致性核对 → 输出含语义元数据的产物。

首轮冻结范围：标准节点向量和壳/实体应力；明确支持的层/积分点；已映射的历史变量；常用 ASCII/binout 分支；两点/区域定义的相对位移、力—位移/工程应力—应变、明确能量项的预算筛查；统一色标静态图和有界时序输出。没有可靠原生含义的历史槽位必须拒绝解释。

退出标准：数值/图像来自同一量和选择；与已知合成真值及代表性原生输出对照；缺变量、失效实体、分片缺失不静默跳过；工程换算前提明示。成功完成提取不等于模型物理有效或准静态成立。

### WF-AUTO：录制、参数化与可恢复复用

用户任务示例：“把刚才这套操作保存成模板，替换模型、选区、阈值或工况参数后重复执行。”

步骤：记录输入/版本/受管操作与原始程序 → 提取显式参数 → 校验参数和依赖 → 在新任务或恢复会话中回放 → 每步结果/质量断言 → 故障定位与安全续跑 → 汇总产物与执行差异。

首轮冻结范围：受管工具工作流、已验证 cfile 子集、五种脚本入口的明确依赖/产物；线性流程与必要的断言/参数迭代。任意手工鼠标动作、任意脚本的语义理解、多模型自动重映射均不默认包含。

退出标准：换参数后实际输出改变且符合预期；旧输出不能冒充新结果；版本/模型不匹配可解释拒绝；中断后不重复执行不确定修改；两条前后处理流程能被记录和复用。

## 3. 统一架构

```text
自然语言任务 / 客户端
          ↓
Skills：理解任务、补齐工程参数、选择经过认证的流程
          ↓
工作流层：步骤、依赖、参数、质量断言、检查点、恢复
          ↓
统一语义对象与操作合同
          ↓
选择 | 网格 | 模型/关键字 | 检查 | 结果 | 工程曲线 | 显示 | 脚本 | 模板
          ↓
执行适配器：LS-PrePost GUI / cfile / SCL / 应用内 Python
可选适配器：PyDYNA / LASSO / LS-Reader
          ↓
输入与产物、日志、数值/结构/图像检查、版本证据
```

原生命令、SCL、Python 是执行渠道，不是三套彼此独立的产品功能。相同“提取单元应力”必须共享实体、状态、单位、积分点、平均等合同，再由适配器实现。GUI 与无 GUI 的差别也由执行上下文表达，不能让上层工具随意切换实例。

用户要求原生 LS-PrePost 时，不能悄悄改走读取器然后报告原生成功。PyDYNA 用于关键字构造/编辑，读取器用于明确标注的结果访问或交叉核验；它们不承担 LS-PrePost GUI 的职责。

### 必须统一的语义对象（目标，不是现有实现声明）

| 对象 | 必须表达的内容 | 当前缺口 |
|---|---|---|
| ModelRef | 文件族/输入身份、模型 ID、keyword/result、单位、引用依赖 | 路径与模型身份分散；复杂 include/多模型不足 |
| SelectionSpec | 模型、实体种类、真实 ID、谓词、可见/有效范围、参考/变形坐标、状态 | keyword 和结果选择未统一；`pall` 副作用需显式化 |
| FieldSpec | 物理量/分量、单位、层/积分点、坐标、平均、有效性掩码 | 数值编号和语义信息分散在 SCL/读取器/显示代码中 |
| CurveSpec | 数据源/实体/分量、时间轴、单位/符号、时间对齐/滤波/参考长度面积 | 已有局部约定，尚无完整公共合同 |
| ExecutionContext | 构建/后端/GUI 模式、拥有的进程、任务目录、预算/超时 | 不同入口创建实例和暂存策略需要统一 |
| OperationResult | 执行状态、范围验证、工程检查结果、产物、警告、恢复信息 | `status=succeeded` 与 `passed_checks=false` 需要工作流门槛统一解释 |

### 功能模块的责任

1. **会话与任务运行时**：版本探测、输入/输出、拥有的进程、串行请求、超时、检查点与证据；不做工程推断。
2. **选择与集合**：统一 keyword/result 选择，ID/几何/拓扑/结果谓词、缓存与集合转换。
3. **网格生成与编辑**：生成、变换、节点/连接、合并/拆分、法向；不自行决定材料。
4. **模型与关键字**：部件、材料/截面、载荷/边界/接触、集合、编号和引用保真。
5. **检查与质量**：原生检查、几何/引用交叉检查、可定位问题、明确判定门槛；不自动全局清理。
6. **结果提取**：文件族、实体/状态/变量/积分点数据，缺失与有效性标记；不隐含工程换算。
7. **工程量与曲线**：张量不变量、相对运动、工程曲线/能量、单位/符号/时间对齐。
8. **显示与产物**：相机、显隐、色标、云图、动画、报告；使用相同 SelectionSpec/FieldSpec。
9. **脚本与工作流**：原始五种入口、宏、录制、参数、依赖/断言与回放。
10. **安装资源与案例模板**：把过滤器/模板/案例组织成工程任务；不把模板加载当作工况完成。

已有 110 个 Service 操作已在机器计划中逐个归属模块，另有 4 个知识检索接口。一个工具可以被多条流程复用，但只有一个主要维护模块；模块数量/工具数量不是覆盖率。

## 4. 当前代码的保留与整合

保留：标准 MCP/CLI 注册入口、已有 Service 外观、拥有进程的会话控制、通过验收的原生命令配方、结果张量/曲线数学、产物身份检查和原生反例。

逐步整合，不推倒重写：

| 当前结构 | 下一步收敛 |
|---|---|
| `Service` 的多组 mixin、`registry.py` | 对外接口先兼容，内部逐模块采用统一输入/输出合同，防止新增重复工具 |
| `sessions.py`、`runner.py`、`programs.py`、`native_results.py` | 统一 ExecutionContext 和执行证据；GUI 请求不能隐式变成后台实例 |
| `gui_mesh.py` 的统一前后整模保存/读回 | 拆分只读、选区、修改事务；按变更范围验证，解决性能与 20000 限制 |
| `gui_selection.py` 与结果工具各自的实体过滤 | 收敛 SelectionSpec；明确显隐/有效实体和模型身份 |
| SCL/读取器/Python 中分散的变量与积分点规则 | 收敛 FieldSpec 和版本能力探测，不把不同编号直接互换 |
| `workflows.py` 线性步骤与简单 status 判断 | 加入质量断言、条件失败、参数迭代及确定性恢复；先覆盖三条主流程需要的能力 |
| 当前资料/能力/工作流多个 JSON 与文档 | 由 development_plan 连接模块、来源、待办、流程和里程碑；CI 验证引用，不再各写各的 |

优先修复影响完整流程的共用接口；不先做大规模目录搬家或仅为“架构漂亮”改写已通过的代码。

## 5. 开发依赖与版本顺序

当前进入 **R0：设计与基线对齐**。退出后按以下依赖推进，允许独立的软件逻辑并行验证，但不再按哪个按钮容易点击来选开发主题。

```text
语义合同 + 操作结果/质量断言
          ↓
模型/选区/结果的按需访问 + 会话事务
          ↓
常用网格编辑             结果/工程曲线
          └─────┬─────────┘
                ↓
三条流程集成 + 录制/参数复用 + 可重复原生验收
                ↓
0.4 首个实用版本（明确支持矩阵）
                ↓
常用子功能扩展 → 模板工程化 → 旧版本/两种无 GUI 模式 → 后排几何/高级模块
```

- **R1：首个实用版本收口**。三条主流程必须共同验收；不再只完成前处理而长期拖住 Post。具体实施从共用合同/断言/选区开始，随后补各流程缺失操作。
- **R2：常用功能矩阵扩展**。按选择、Model、Mesh、EleTol、Post 的约定操作清单扩展，优先级来自工程任务频率与依赖；每个子模块都有完成边界。
- **R3：模板与复杂模型工程化**。7 个模板、常用材料/边界/接触、include/多模型和参数工况。
- **R4：兼容性推广**。4.8/4.10/4.13 按功能验证；在可见 GUI 主流程完成后适配两种无 GUI 模式。
- **R5：几何和高级应用**。保持用户要求的后排顺序；求解服务单独立项验收。

版本标签只在退出标准满足后发布，不为满足时间或工具数量提前标“完成”。目前没有依据给出全部开发工期或百分比。

## 6. 每个开发项的完成定义

一个事项应先具有：用户任务、所属模块、输入/输出语义、依赖、对应来源、失败情况和验收条件。再实现代码，并同时提交：

1. 正式工具/内部操作及 Skill 路由。
2. 相关逻辑/边界测试，不机械复制实现。
3. 指定构建的原生正常例与失败例；需要 GUI 的项目必须做可见 GUI 验收。
4. 坐标/连接/引用或数值/图像/文件一致性证据。
5. 版本、规模、后端和未覆盖范围。
6. 完整流程中的集成验收，而不只证明单个按钮有效。

只有代码存在时记“实现”；实机通过但范围受限时记“限定原生验收”；整个来源或模块不能因为一个案例通过就标完成。菜单导航记录和通用脚本入口不直接提高功能覆盖状态。

## 7. 资料如何服务设计

资料是模块合同与验收样例的依据：官方手册定义软件语义，教程定义可复现任务，本地案例暴露需求/错误，PyDYNA 提供关键字构造，LS-Reader/LASSO 提供可选读取与对照，公开仓库提供实现经验，视频补充 GUI 操作。对应记录见 [资料转化矩阵](SOURCE_ADOPTION.md)。

不能以“把文件下载了/索引了/类列出来了”报告吸收完成，也不直接复制所有上游代码。一个来源通常为多个模块提供依据；一个模块也需要多种来源交叉核对。私有资料只记录可公开的能力结论。

## 8. 防止开发再次失去主线

- 每次开发先指明哪个模块、哪条主流程、哪个待办/里程碑；没有归属的事项先归类。
- 新工具先检查已有模块是否能扩展，保留对外兼容，避免把每个按钮机械封成独立 API。
- 每批结束报告“哪条用户流程更完整、还卡在哪个环节”，不只报告工具数/测试数/提交数。
- 机器计划中的来源、正式操作、待办、流程和文档引用由 `tools/validate_development_plan.py` 检查，并纳入 CI。
- 本文件的目标架构与当前实现明确分开。设计落地通过代码迁移和完整流程验收证明，不能靠新增这份文档自称已完成架构改造。
